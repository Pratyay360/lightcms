# Astro + Starlight Template Reference

The `astro_blog` template is a documentation-first starter with a small blog. It is the right choice when the user wants guides, docs, and a few posts in one site, or when they want Astro's component model and content collections.

## Layout

```text
.
├── astro.config.mjs
├── package.json
├── public/favicon.svg
├── src/
│   ├── components/
│   │   ├── Button.astro
│   │   └── Footer.astro
│   ├── content.config.ts
│   ├── content/docs/
│   │   ├── index.mdx          # splash home
│   │   ├── intro.md           # a normal docs page
│   │   └── blog/
│   │       ├── first-post.md
│   │       └── second-post.md
│   └── styles/
│       ├── global.css
│       └── custom.css
├── .github/workflows/ci.yml
├── mise.toml
├── LICENSE
└── README.md
```

LightCMS shows the top-level `src` collection. Writers work in `content/docs/blog`. This is intentional: moving content to a root `posts/` folder would require a custom content loader and would fight Starlight's conventions.

## Configuration

```js
// astro.config.mjs
import starlight from "@astrojs/starlight";
import { defineConfig } from "astro/config";

export default defineConfig({
  site: "https://example.github.io/",
  base: "/my-blog",
  integrations: [
    starlight({
      title: "My Blog",
      description: "A short description.",
      customCss: ["./src/styles/global.css", "./src/styles/custom.css"],
      pagefind: true,
      tableOfContents: { minHeadingLevel: 2, maxHeadingLevel: 3 },
      pagination: true,
      sidebar: [
        { label: "Start here", items: ["intro"] },
        { label: "Blog", autogenerate: { directory: "blog" } },
      ],
    }),
  ],
});
```

Change both `site` and `base`:

- GitHub Pages project site: `site: "https://<user>.github.io"`, `base: "/<repo>"`.
- User site or custom domain: `site` is the full origin, `base` is `"/"` (or omitted).
- Cloudflare Pages / Vercel / Netlify: usually `base: "/"`.

A wrong `base` is the most common Astro deployment failure. Links generated by Starlight include the base automatically; hand-written absolute links such as `href="/intro/"` do not. Use `import.meta.env.BASE_URL` or Starlight's link helpers for hand-written links.

## Content and front matter

`src/content.config.ts` uses the Starlight loader and schema:

```ts
import { defineCollection } from "astro:content";
import { docsLoader } from "@astrojs/starlight/loaders";
import { docsSchema } from "@astrojs/starlight/schema";

export const collections = {
  docs: defineCollection({ loader: docsLoader(), schema: docsSchema() }),
};
```

A post:

```markdown
---
title: First Post
description: What this starter includes.
date: '2026-01-10T00:00:00Z'
draft: false
tags:
  - intro
---

Body text.
```

Starlight's schema requires `title`; `description` is used for SEO. `draft` is a native Starlight field: `true` keeps the page out of production builds and autogenerated sidebars. `date`, `tags`, and `keywords` are not part of the default schema; if a custom page needs them, extend the schema so they are not stripped:

```ts
import { z } from "astro/zod";

// src/content.config.ts
export const collections = {
  docs: defineCollection({
    loader: docsLoader(),
    schema: docsSchema({
      extend: z.object({
        date: z.string().optional(),
        tags: z.array(z.string()).default([]),
        keywords: z.array(z.string()).default([]),
      }),
    }),
  }),
};
```

Do not promise a date-sorted blog unless you add the UI for it. Starlight does not render dates, tags, or a post list from this front matter by itself.

If the site is really a blog, either:

- use the `starlight-blog` plugin, which adds post listings, dates, authors, tags, and RSS; or
- create a custom Astro page that queries the collection and renders a list.

The minimal template is a docs site with a blog folder, not a full blog engine.

## URLs and slugs

Starlight derives the page ID from the file path:

```text
src/content/docs/blog/hello-world.md  →  /blog/hello-world/
```

LightCMS's default timestamp filename therefore becomes `/blog/1792167272/`. Fix it in one of two ways:

1. **Preferred:** tell writers to replace the Slug field with a human slug. The filename is the URL.
2. Add a custom ID function to the loader if the project must tolerate timestamps:

```ts
docsLoader({
  generateId: ({ entry, data }) => {
    const title = typeof data.title === "string" ? data.title : entry;
    const slug = title
      .toLowerCase()
      .replace(/[^a-z0-9]+/g, "-")
      .replace(/^-|-$/g, "");
    const directory = entry.includes("/")
      ? entry.slice(0, entry.lastIndexOf("/") + 1)
      : "";
    return `${directory}${slug}`;
  },
});
```

The directory prefix matters: returning only the title would turn `blog/hello-world.md` into `/hello-world/` instead of `/blog/hello-world/`. The second option can collide when two posts share a title; append a short suffix if needed. It also makes the ID independent of the filename, which can surprise writers who rename files. Pick one rule and document it.

Starlight also supports a `slug` front matter field to override the ID. LightCMS does not expose `slug` as a normal field, so do not rely on writers filling it in.

## Drafts

Starlight honors `draft: true` natively: the page is available in `astro dev` but excluded from `astro build`, and autogenerated sidebars leave it out of production. That matches LightCMS's draft flag, so the template can use it directly.

A custom blog index that queries `getCollection("docs")` still needs a filter if it should hide drafts during local development. The production build already excludes them.

Do not add a second draft mechanism unless the template has a reason to; the native flag is the one LightCMS writes.

## Build and CI

```toml
# mise.toml
[tools]
node = "latest"
bun = "latest"

[settings]
experimental = true

[tasks]
install = "bun install"
start = "bun run dev"
build = "bun install && bun run build"
preview = "bun run preview"
deploy = "mise run build"
```

`bun run build` writes `dist/`.

```yaml
name: ci

permissions:
  contents: read
  pages: write
  id-token: write

on:
  workflow_dispatch:
  pull_request:
  push:

jobs:
  ci:
    runs-on: ubuntu-latest
    container:
      image: ghcr.io/jdx/mise:2026.9.2
    steps:
      - uses: actions/checkout@main
      - uses: actions/cache@main
        with:
          path: |
            ~/.cache/mise
            ~/.local/share/mise
          key: mise-${{ runner.os }}
          restore-keys: mise-${{ runner.os }}
      - run: |
          mise trust
          mise deps
          mise install
          mise run build
      - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        uses: actions/upload-pages-artifact@main
        with:
          path: ./dist
      - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
        id: deployment
        uses: actions/deploy-pages@main
```

Starlight's `pagefind: true` builds the search index during `astro build`; do not add a separate index task unless the project also uses a custom Pagefind setup.

## Assets and styling

- `public/` is copied as-is. Reference files with the base path, e.g. `/my-blog/favicon.svg` or `import.meta.env.BASE_URL`.
- `src/styles/global.css` imports Tailwind in the org template.
- `src/styles/custom.css` holds the Starlight CSS variables. Keep the light/dark pairs together.
- `src/components/Footer.astro` is wired through `components.Footer`. If you remove the file, remove the config entry.
- The org template uses `starlight-theme-exquisitus` and Tailwind. Remove either dependency if the user wants a leaner site; the build must still pass.

## Cleanup before shipping

The org repository contains a stray `src/content/docs/blog_0/1792181567.md` and an empty `blog_0/.gitkeep`. Remove them. Rename epoch-named sample files to human slugs. Check that `astro.config.mjs` does not still point at `light-cms/astro_blog` or the `astro_blog` base path.

## Verify

```bash
rm -rf dist node_modules
mise trust
mise run build
```

Then check:

- `dist/index.html` exists and renders the splash page.
- `dist/blog/first-post/index.html` exists.
- Links include the configured base path.
- Pagefind assets exist if `pagefind: true`.
- The 404 page exists (Starlight provides one).
- The sample post's `date` does not break the build; Starlight ignores it, but a custom schema might not.
